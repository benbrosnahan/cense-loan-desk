# A11Y-02: Toast status region is not announced

**P1** · effort S · Accessibility

The toast's status region is added to the page already holding its message, so desktop screen readers such as NVDA and JAWS likely never announce 'Saved', 'Removed' or the Undo offer, and Undo itself announces nothing.

| | |
|---|---|
| Who it hurts | Desktop screen-reader borrowers (about 9 in 10 screen-reader users use a desktop at least as often as a phone, per WebAIM) are likely never told that a loan was saved or removed, that their loans or records were cleared, or that Undo is available for 7 seconds; after Save, Save changes, Remove and both Clears focus also falls to the page, so they get no feedback at all. Nobody hears anything after pressing Undo. |
| Standard | WCAG 2.2 SC 4.1.3 Status Messages (AA). Failure F103: steps 1 to 3 hold (the role is set at the same moment the content is added, which W3C says predicts a failure); step 4, whether assistive technology announces it, rests on published tests and Chrome's platform events, not on a run against this app. Technique ARIA22 step 1 (the status container exists before the message) is not met; ARIA22 is a sufficient technique, so missing it does not decide conformance on its own. The silent Undo is a usability gap, not a 4.1.3 failure. |

## Measured

Shipped build on port 3100, at 1440 and 375 wide (Remove also on the live deployment):
- Before the first toast the page has 0 [role=status], 0 output and 0 aria-live elements in the light DOM. Next's route announcer is a separate, always-empty role=alert inside a shadow root and never receives toast text.
- 9 of 9 say() paths insert the region with a single appendChild that already holds the full text, for example 'Removed 2023–24 subsidizedUndo'. A second message while a toast is still up changes the text in place on the same node.
- Chrome 146 and 150 on macOS (chrome://accessibility): the shipped Remove and 'Snapshot saved' fire AXLiveRegionCreated only, with no AXLiveRegionChanged. Text added to an existing role=status region fires AXLiveRegionChanged. In Chromium's source the Windows layer lists the created event as unused and fires live-region events only for changed, and the macOS layer notes that VoiceOver needs a changed notification but sends only created for a new region.
- Undo: rows go back from 7 to 8 (8 stored), with zero live-region operations, focus on BODY, and nothing in the next 3.2 s.
- Published tests of the same DOM pattern (TetraLogical matrix, 2024, 'Populated live region via JS'): role=status is not announced by NVDA or JAWS in Chrome or Edge, or by VoiceOver on macOS in Chrome, and is announced by VoiceOver on iOS Safari. Writing into an existing region ('Inject into existing live region') is announced on all of those pairs. NVDA issue 14591 on this behaviour was closed as not planned.
- WebAIM screen reader survey 10: 40.2% of respondents use a screen reader mostly on desktop and 49.5% about equally on desktop and mobile; primary desktop readers are JAWS 40.5%, NVDA 37.7% and VoiceOver 9.7%.
- No screen reader was run against this app by the filer or by any skeptic.

## Required

The status container is in the DOM, empty, before any message is written into it (ARIA22 step 1), so each message arrives as a change that screen readers announce. After Undo, a short status message says what came back.

## Reproduce

1. With NVDA or JAWS and Chrome on Windows (or VoiceOver and Chrome on a Mac), open the app and choose 'Look around with example loans'.
2. Open the 'Freshman subsidized' row and press Remove. The toast shows 'Removed Freshman subsidized' with Undo; per the published tests the reader says nothing.
3. Press Undo. The loan comes back and nothing is announced, on any reader.
4. Without a screen reader: in DevTools run document.querySelectorAll('[role=status]').length before pressing Remove (0) and right after (1, already containing the text).

Or run its test from `audits/`: `AUDIT_SHOW_KNOWN=1 npx playwright test -g "A11Y-02"`.

## Fix

Keep the status region mounted and empty, so every message is written into a region that already exists, and have each Undo say what it restored.

```tsx
// src/components/shared/ui.tsx, Toast: delete the early return at :578 and always render the region
return (
  <div
    role="status"
    aria-live="polite"
    className="no-print pointer-events-none fixed inset-x-0 bottom-0 z-50 flex justify-center px-4 pb-[max(1.25rem,env(safe-area-inset-bottom))]"
  >
    {toast && (
      <div className="rise pointer-events-auto flex items-center gap-1 rounded-full bg-slate-900 py-1.5 pl-5 pr-1.5 text-sm font-semibold text-white shadow-lift">
        <span className="py-1.5 pr-3">{toast.message}</span>
        {toast.action && (
          <button
            type="button"
            onClick={() => {
              onDismiss(); // first, so the message the restore sets is not cleared
              toast.action!.run();
            }}
            className="...unchanged..."
          >
            {toast.action.label}
          </button>
        )}
      </div>
    )}
  </div>
);
```

```ts
// src/app/page.tsx, the three Undo restores
// deleteLoan, :257 (gone is in scope here)
run: () => { setLoans(before); say(`Restored ${gone?.nickname ?? "loan"}`); },
// clearLoans, :265
say("All loans cleared", { label: "Undo", run: () => { setLoans(before); say("Loans restored"); } });
// clearSnapshots, :271
say("Records cleared", { label: "Undo", run: () => { setSnapshots(before); say("Records restored"); } });
```

The reorder at ui.tsx:593-594 is required: in the shipped order onDismiss() runs last and clears the new message (measured: the region is empty after Undo without it). No new dependency; nothing leaves the device.

## Severity

Desktop screen-reader users (NVDA or JAWS in Chrome or Edge, VoiceOver in Chrome on a Mac) likely hear nothing on the first confirmation of every add, edit, remove or clear, and after Save loan, Save changes, Remove and both Clears the toast is their only feedback because focus falls to the page: an SC 4.1.3 AA failure in the core loan-entry flow. It is inferred from Chrome's accessibility events and published screen-reader tests rather than a screen reader run on this app; if one NVDA and Chrome check shows the toast is read, this drops to P3.

Proposed P1; independent severity judges said P1; final P1.

## Verification

Confirmed by 3 of 3 skeptics (reproduce, standards, impact) on the DOM sequence, Chrome's accessibility events and Chromium's source; no screen reader was run on this app, so the spoken outcome rests on published tests.
