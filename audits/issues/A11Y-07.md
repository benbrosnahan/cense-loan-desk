# A11Y-07: Input borders below 3:1

**P2** · effort S · Accessibility

Text input and select borders are only 1.48:1 against white, so a low-vision borrower adding a loan cannot see the outline of the empty Name field, and every other field looks faint.

| | |
|---|---|
| Who it hurts | Low-vision borrowers adding or editing a loan cannot see where the empty Name field sits or how far it extends (its label and hint stay readable), and every other field's outline reads faint. |
| Standard | WCAG 2.2 SC 1.4.11 Non-text Contrast (AA) |
| Where | The clear case is the empty Name field (#nickname) in the Add a loan form, inside 'Add more detail', which is closed by default for a new loan. The same border is on all 11 text inputs and selects: #disb, #balance, #rate, #servicer, #nickname, #principal and #minp in Add a loan; #income and #household on Plans; #extra and #planswitch on the slate-50 panel in Payoff. Measured at 320, 375, 768, 1024 and 1440 in Chromium, with pixel checks at 375. iOS Safari not tested. |
| Code | [`src/components/shared/ui.tsx:290`](../../src/components/shared/ui.tsx#L290), [`src/components/shared/ui.tsx:292`](../../src/components/shared/ui.tsx#L292), [`src/components/loans/LoanForm.tsx:446`](../../src/components/loans/LoanForm.tsx#L446), [`src/components/loans/LoanForm.tsx:423`](../../src/components/loans/LoanForm.tsx#L423), [`tailwind.config.ts:19`](../../tailwind.config.ts#L19) |
| Test | `a11y.spec.mjs`: "A11Y-07 every text field and select has an outline of at least 3:1 at rest and on hover" |

## Measured

At rest every field's border is #BFDCB8 (border-slate-300; tailwind.config.ts remaps slate to the brand greens): 1.48:1 against the white field and the white card, and 1.33:1 against the slate-50 panel behind #extra and #planswitch. Hover (#8CA98E, hover:border-slate-400) is 2.57:1. Focus navy (8.01:1) and invalid red-600 (4.83:1) pass. Ten of the 11 fields show a placeholder, value, affix, select arrow or Chromium's date mask inside the border (the placeholder colour, slate-500, is 4.51:1), so for them the border is not the only cue. The empty #nickname has no placeholder, value or affix: its 1.48:1 border is the only sign of where the field is, with its label 6px above and its hint 6px below. Pixel samples at 3x match computed style: #FFFFFF #BFDCB8 #FFFFFF across the edge at rest, #8CA98E on hover.

## Required

3:1 against adjacent colours for any visual information needed to identify a control, and hover must not drop it below that (WCAG 2.2 SC 1.4.11 and its Understanding document). Understanding Figure 32, a labelled white text input whose complete border is its indicator, says that border must meet 3:1.

## Reproduce

1. Open http://localhost:3100 in a fresh browser window (the first-run screen), about 375px wide.
2. Tap 'Add my first loan', then 'Add more detail'.
3. Look at Name: a label above, a hint below, nothing inside, and an outline of #BFDCB8 on white (1.48:1). Hover it: #8CA98E (2.57:1). The other fields in the form have the same outline but show $, %, a placeholder, a value or a date mask inside.
4. For the panel case: reload, tap 'Look around with example loans', open Plans and choose a plan (for example 'Use <plan name> as my plan' on the top pick), then open Payoff: the 'Extra each month' field outline is 1.33:1 against the panel.

Or run its test from `audits/`: `AUDIT_SHOW_KNOWN=1 npx playwright test -g "A11Y-07"`.

## Fix

In src/components/shared/ui.tsx, darken the shared inputClass border at rest and on hover. Every text input and select in the app uses inputClass, so this one change covers all 11 fields:

```diff
 export const inputClass = cn(
-  "w-full min-h-[48px] rounded-2xl border border-slate-300 bg-white px-3.5 py-2.5 text-base text-slate-900",
+  "w-full min-h-[48px] rounded-2xl border border-slate-500 bg-white px-3.5 py-2.5 text-base text-slate-900",
   "placeholder:text-slate-500 transition-colors",
-  "hover:border-slate-400",
+  "hover:border-slate-700",
```

slate-500 (#5C7F5F) is 4.51:1 on white and 4.04:1 on the slate-50 panel; slate-700 (#3A6B3E) is 6.26:1 and 5.62:1. Built in a scratch copy (tsc 0, build 0): rest rgb(92, 127, 95), hover rgb(58, 107, 62), focus rgb(39, 91, 45), and an invalid field stays rgb(220, 38, 38) at rest, on hover and on focus. The darker outline is a visible design change, so compare the before and after screenshots listed under reproduce before shipping.

## Severity

Low-vision borrowers meet the faint outline on every field each time they add or edit a loan, but the only field where the outline is the sole cue is the optional Name field, collapsed under 'Add more detail', whose readable label focuses it when clicked. No step of the core flow is blocked or misread, so this is a bounded defect rather than a core-flow WCAG failure, and the 1.4.11 call on a labelled empty field is the prevailing reading, not a settled one.

## Verification

Confirmed by 2 of 2 skeptics (reproduce, standards); both kept P2.

<details><summary>Dissent and notes</summary>

No skeptic refuted the finding or changed its severity. The standards skeptic confirmed it on the prevailing reading of 1.4.11 but called it a judgement: W3C's own failing example (Figure 45) is an input with no label, #nickname has a visible label, and w3c/wcag issue 1091 and PR 5362 are still open on exactly this case, with one working-group participant questioning whether a label above the field, rather than one floating inside it, should decide pass or fail. So the filing's 'strict failure' and 'nothing else to show it' overclaim, and its impact 'cannot find the empty Name field' is softened here to 'cannot see where it sits or how far it extends'; the reproduce skeptic said the same. Both skeptics raised one untested hypothesis: iOS Safari may draw an empty date field with no text, which would make the required #disb a second field where the border is the only cue and could raise the severity. Neither could test it (no iOS simulator on this Mac). Evidence correction from the standards skeptic, applied above: the lead's input-shipped.png shows Name in its hover state, and that skeptic's own squint-shipped.png and squint-patched.png were rendered and then discarded as misleading.

One member, nothing to merge. Fix kept as filed: slate-500 at rest and slate-700 on hover are existing palette tokens, the change was built and measured, and it leaves the focus and invalid states alone. If the darker outline looks too heavy, the standards skeptic computed #769379 as a lighter option (3.38:1 on white, 3.03:1 on slate-50) but did not build it; with that option hover must still reach 3:1, so hover:border-slate-400 (2.57:1) would have to change too. Check the date field once on a real iPhone, since that is the open question that could raise the severity. The README's contrast check covers text only (README.md:74), which is why this was missed. Other slate-300 borders (secondary buttons, choice buttons, the Payoff presets) surround visible text, so Understanding's Boundaries note exempts them, and they are not part of this issue. If DX-04's palette rename lands first, the classes become border-forest-500 and hover:border-forest-700. No runtime dependency is added and nothing leaves the device.
