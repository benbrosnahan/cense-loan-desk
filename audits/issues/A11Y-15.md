# A11Y-15: Repeated controls share one name

**P3** · effort S · Accessibility

Each plan's 'How this plan works' button on the Plans tab has the same name, so a screen-reader borrower who lists the page's buttons cannot tell which plan each one opens.

| | |
|---|---|

| Standard | WCAG 2.2 SC 2.4.6 Headings and Labels (AA), as best practice for controls listed out of context: read in order, each card's h3 names the plan, so no criterion fails, and axe 4.11.2 reports 0 violations on Plans. ## Measured

Chromium accessibility tree on the production build:
- Plans at 375 and 1280: 15 buttons; 'How this plan works' 4 times, and 'Hide the detail' 4 times once all four are open (0 by default). None has aria-label, aria-labelledby or aria-describedby; the plan name is only in each card's h3 (Standard, Graduated, IBR, RAP). The count follows the number of open plans.
- 'Use Standard as my plan' appears twice with no plan chosen (hero and row), and also when the chosen plan is not the top pick; both call onSelectPlan with the same id (PlansPanel.tsx:370 and :411).
- Landmarks on Plans: main, region 'Summary', navigation 'Sections'. The recommendation is the text 'WHERE WE WOULD START' followed by h2 'Standard', with no region or name of its own.
- Section bar: 'Your loans', 'Repayment plans', 'Payoff', 'Records' at 1440 and 'Loans', 'Plans', 'Payoff', 'Records' at 375; Records becomes 'Records1' after one snapshot at both widths ('Records2' after two).
- A Playwright journey with default substring names hit 4 strict-mode errors at both widths (nav Plans, 'Use RAP as my plan', Payoff, Records); exact names hit 1 (the plan button) and found 0 'Records' after a snapshot. axe 4.11.2: 0 violations on Plans.
Fixes as measured:
- The plan name in the visible disclosure text, production build: 0 duplicate button names, closed and open, at 375 and 1280.
- The region, hero label, nav labels and Records description, scratch build (next build with type checks passed): region 'Recommended plan' found; 0 duplicate button names on Plans in all three selection states at both widths, including with every disclosure open; the same nav names at both widths; Records keeps its name, with description '1 saved'; axe adds no violation in the form, Plans, Payoff or Records, and its experimental SC 2.5.3 rule reports 0 violations. Exact names then give 0 strict-mode errors at 1440; default substring names still give 4.

## Required

Each control's name makes sense out of context (which plan it opens or picks), the recommendation can be found by name, and the section-bar names stay the same at every width and after a snapshot, while every name still contains its visible text (SC 2.5.3).

## Reproduce

1. Open http://localhost:3100 with no saved data and click 'Look around with example loans'. Open Plans, enter 52000 as yearly income and do not choose a plan.
2. List the buttons with a screen reader (VoiceOver rotor, NVDA Insert+F7) or read them in Chrome DevTools > Accessibility: 'How this plan works' appears four times, once per open plan, and the top pick's 'Use ... as my plan' twice, in the recommendation and in that plan's card. Open all four plans and 'Hide the detail' appears four times.
3. Compare the section bar at 1440 wide ('Your loans', 'Repayment plans') with 375 wide ('Loans', 'Plans'). On Records click 'Save today's snapshot': the Records button is now named 'Records1'.

Or run its test from `audits/`: `AUDIT_SHOW_KNOWN=1 npx playwright test -g "A11Y-15"`.

## Fix

Four small edits, names only; nothing changes on screen except the disclosure text.

1. src/components/plans/PlansPanel.tsx:223. Say which plan each disclosure opens.
```tsx
{open ? `Hide the ${meta.name} detail` : `How ${meta.name} works`}
```

2. PlansPanel.tsx:344, with its closing tag at :381. Give the recommendation a name of its own.
```tsx
<section aria-label="Recommended plan" className="rounded-3xl bg-navy p-5 text-white shadow-lift sm:p-7">
```

3. PlansPanel.tsx:368-374. The hero's button stops repeating the plan row's name, and its name still starts with its visible text.
```tsx
<button
  type="button"
  aria-label={`Use ${PLAN_META[top.estimate.id].name} as my plan, our recommendation`}
  onClick={() => onSelectPlan(top.estimate.id)}
```

4. src/app/page.tsx:519-537. Section-bar names that do not change with width or saved records; the count moves to the description.
```tsx
<button
  key={t.id}
  onClick={() => goTo(t.id)}
  aria-current={tab === t.id ? "page" : undefined}
  aria-label={t.long}
  aria-description={
    t.id === "history" && snapshots.length > 0 ? `${snapshots.length} saved` : undefined
  }
  ...
>
  ...
  {t.id === "history" && snapshots.length > 0 && (
    <span aria-hidden className="tnum ml-1 opacity-75">
      {snapshots.length}
    </span>
  )}
</button>
```

## Severity

Screen-reader borrowers who browse Plans by a list of buttons, and agents or tests that find controls by name, meet the duplicates on every visit to Plans. Read in order, each card's heading names its plan and both 'Use Standard as my plan' buttons do the same thing, so no step is blocked, nothing is wrong and no WCAG criterion fails: polish.

## Verification

Confirmed by 2 of 2 skeptics across 2 filings (a P3 review on each), reproduced with their own probes at 375, 1280 and 1440 wide; both kept P3.

<details><summary>Dissent and notes</summary>

Agentic filing: the P3 reviewer reproduced every value with different code but found three details state-dependent or understated. 'Hide the detail' appears 4 times only with all four plans open. The duplicate 'Use ... as my plan' is not limited to before a plan is chosen; it also occurs when the chosen plan is not the top pick. And the fix does not reduce default substring collisions in Playwright (4 strict-mode errors before and after), because SC 2.5.3 requires the hero's name to contain the row's 'Use RAP as my plan', and the NEXT cards' 'Go to payoff' matches the nav's Payoff; with aria-label={t.long}, exact 'Plans' and 'Loans' also stop resolving at 375. Duplicate-name filing: confirmed with no change; its reviewer noted it is not a clear WCAG failure, because the h3 gives the context when read in order, which is why it is filed as best practice.

Fix choice: for the disclosures, the duplicate-name filing's visible text rather than the agentic filing's aria-label ('How this plan works: Standard'). Both measured 0 duplicate names, but the visible text needs no ARIA, keeps name and label identical, and lets voice-control users say what they see; the longer text may wrap at 320px (not measured). The region, the hero label, the nav labels and the Records description are the agentic filing's. The two parts were built separately, not as one patch. Records: the agentic filing's aria-description keeps the name 'Records' at every count. A11Y-14's names filing proposed screen-reader-only ', 2 saved' instead, which reads 'Records , 2 saved' and still changes the name with each snapshot. aria-description is an ARIA 1.3 attribute that React 18.3 and its types accept; it was checked in Chromium only. The count stays visible but leaves the name, which the reviewer judged acceptable under SC 2.5.3 because the count is not the label. The nav's aria-label={t.long} means 375-wide names no longer start with the visible word ('Plans' sits inside 'Repayment plans'), which SC 2.5.3 allows. A11Y-10 drops opacity-75 from the same count span (page.tsx:534); combine the two edits. A11Y-17 proposes a screen-reader-only 'Where we would start: ' prefix in the hero heading (PlansPanel.tsx:350) with the eyebrow hidden, which fits with the region label. Not measured, from reading the code: with income blank, each plan priced off income shows its own 'Add my income' button (PlansPanel.tsx:135-146), so IBR and RAP repeat that name as well; both do the same thing, and the test seeds an income so it does not trip on them.
